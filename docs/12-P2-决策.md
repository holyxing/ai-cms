## A. 数据库 / 模型类

### A1. P2 表主键用 UUID（与 P1 一致）

**决策**：4 张 P2 表 `id` 全部用 `UUID PRIMARY KEY DEFAULT gen_random_uuid()`，不用 BIGSERIAL。

**为什么**：
- P1 已迁移 13 张表全部用 UUID（sites/contents/media 等），FK 关联
- BIGSERIAL 会导致 P2 表 FK P1 表时类型不匹配
- UUID 跨服务一致 + 迁移友好（无 sequence 冲突）

**影响**：
- 04b §4.1-4.4 DDL 已改（P2 表）
- 04b §0 设计原则保留 BIGSERIAL 描述作历史
- 04b §5 P3 表（D6 同理，P3 启动时再改）

### A2. 主题作用域 = 全局库 + 站级实例（Ghost 模式）

**决策**：
- `themes` 表 = **全局主题库**（无 site_id），所有站共享
- `theme_versions` 表 = **站级应用实例**（有 site_id），记录"这个站用了哪个主题 + 当前 tokens"
- 站点切换主题 = 在 `theme_versions` 创建新 version（is_active=true）

**为什么**：
- 与 04b 原始设计一致（themes 无 site_id）
- Ghost / WordPress.com / Substack 都是这个模式（用户换主题 = 应用层切换，不是买新主题）
- 内置 5 套主题（default/business/tech/magazine/minimal）天然是"库"
- 用户在 default 基础上微调 → 创建 custom theme（`type='custom'`, `base_theme_id='default.id'`）

**影响**：
- 02 API `/sites/{id}/themes` 解读：**应用层过滤**（这个站"能用什么主题"= 全部 5 个 preset + 该站已创建的 custom）
- 02 API `/themes/current` 解读：这个站"当前激活"的主题版本
- 04b `themes` 表改：加 `base_theme_id`（custom 来源追踪）+ `default_tokens`（种子 tokens）
- 04b `theme_versions` 表改：加 `theme_id` FK themes（"用了哪个主题"）

**反例（不采纳）**："每站独立主题库" = 主题数据冗余 + 主题升级时要每站同步。

## B. 主题 / 部署逻辑类

### B1. 新站默认主题 = 启动时 apply 一次

**决策**：
- `themes` 表中 `is_default=true` 的那一条（partial unique index 强制只有一个）
- 新站创建时（`POST /sites` 成功时）→ 自动创建 `theme_versions v1` 引用 `is_default` 主题 → is_active=true
- 应用层保证：所有 default 应用的事务与 site 创建在同一 DB 事务

**实现要点**：
```python
# sites.py create_site 内
db.add(Site(...))
await db.flush()  # 取 site.id
default = (await db.execute(
    select(Theme).where(Theme.is_default == True, Theme.deleted_at.is_(None))
)).scalar_one()
db.add(ThemeVersion(
    site_id=site.id, theme_id=default.id, version=1,
    tokens=default.default_tokens, is_active=True,
    author_id=admin.id,
))
```

**为什么**：避免"建站后立即访问公开站 = 没主题"的尴尬状态。

### B2. 主题切换 = 创建新 version + 触发发布（同步）

**决策**：
- `POST /themes/current/apply` = 选主题库中某主题 → 创建新 theme_version（is_active=true，旧版 is_active=false）
- 切换完成后**不自动发布**（避免用户改主题后立刻被打扰到前台）
- 切换成功后返回 200 + 新 version 详情，前端 toast "已切换到 [主题名]，去发布？"

**为什么**：用户可能想"先切后调"，调完再决定发布时机。

### B3. 主题 token 编辑器 = 改即存新 version

**决策**：
- `PUT /themes/current` body = 部分 token 更新（如只改 `color.primary`）
- 后端 = 创建新 theme_version（v+1），tokens = 当前 v 的 tokens + 改动，is_active=true
- 旧 version 不删（保留历史可回滚）

**为什么**：所有改动都可追溯 + 可回滚。代价是 theme_versions 表会增长，但每站一个主题每改一次一行，量级可控。

### B4. 预览 iframe = 客户端 mock 渲染（短期） / SSG 预发布（V2）

**决策**：
- **P2 短期**：编辑器右侧"预览"标签 = 客户端组件，**读最新 tokens + 内容 JSON 实时渲染**（不调后端）
  - 优点：零延迟、零依赖
  - 缺点：与最终 SSG 产物可能有微小差异（CSS 解析、字体加载）
- **P2.5 优化**：发布前可点"预发布预览"= 触发 SSG 完整构建到 `/data/sites/{id}/preview/`，iframe 加载该路径
  - 优点：与生产零差异
  - 缺点：每次预览要等构建

**P2 范围内只做"客户端 mock 渲染"**。客户端渲染器复用 SSG 模板的 Block 组件代码（共享 `tiptap-to-html` 包或 monorepo workspace）。

### B5. 多域名 → 静态产物映射

**决策**：
- nginx 主配置 = `server_name _`（catch-all）
- 解析 Host 头 → 查 `site_domains` 表（Redis 缓存）→ 反代到 `/data/sites/{site_slug_or_id}/public/`
- 缓存策略：域名 → 站点 ID 映射 cache 5 分钟，站点归档 cache 1 分钟

**实现要点**：
```nginx
server {
  listen 80;
  server_name _;
  location / {
    # 通过 lua 查 redis 取 site_id
    set $site_id "";
    access_by_lua_block {
      local redis = require "resty.redis"
      local r = redis:new()
      r:connect("redis", 6379)
      local v = r:get("domain:" .. ngx.var.host)
      if not v then ngx.exit(404) end
      ngx.var.site_id = v
    }
    root /data/sites;
    try_files /$site_id/public$uri /$site_id/public$uri/ /$site_id/public/index.html =404;
  }
}
```

**注**：实际实现可能用 OpenResty 自带 lua 或简单 Python 反代。P2 起步用 Python 反代更简单（FastAPI 路径），nginx 兜底。

**反例（不采纳）**：每个站一个 nginx server block（站点多了配置文件爆炸）。

### B6. SSG 构建 = 全量 + 并行（每站 1 次）

**决策**：
- 1 站点 1 次构建 = 渲染该站点下所有 published 内容（snapshot 模式：读 content_snapshots）
- 多站点并行触发：Celery 队列并发跑（每 worker 一次 1 站点，避免资源争抢）
- 单 worker 串行处理 = 不阻塞其他 worker
- 增量构建 = V2（先全量够用）

**性能预期**：
- 100 篇文章 / 站点 = 构建时间 < 30s
- 1000 篇文章 = < 3min
- 5 站点同时构建 = 各跑各的（多 worker）

### B7. 公开站 footer 显示 "Last built: ..."

**决策**：
- 公开站 SSG 产物在 layout 里嵌入 `{{ build_time }}` 模板变量
- 构建时由 Astro fill 当前时间
- 用户访问公开站能直接看到"这站是不是最新"

**为什么**：解决"我发了文章，公开站看不到"的疑虑（用户层面最重要的反馈信号）。

## C. UX / 体验类（用户视角）

### C1. 主题预览图 = 5 主题先用占位

**决策**：
- P2 起步：5 主题用统一占位预览（`/static/theme-preview-placeholder.png`，灰底 + 主题名 + 主色块）
- P2.5 优化：每个主题真实截图（用 Playwright 跑 SSG 产物截图）
- 用户看"占位"也能区分主题（颜色 + 名称），够用

### C2. 主题编辑器实时预览 = 纯前端 CSS 变量刷新

**决策**：
- 主题编辑面板（前端）调 token → 写入 form state → iframe 内的 CSS 变量同步更新
- 不用等"保存" → 用户拖滑块立刻看到效果
- "保存"按钮 = 调 `PUT /themes/current` 创建新 version
- 撤销/重做：编辑面板本地 history（不依赖服务端），保存前可任意撤销

### C3. 主题编辑器撤销 = 本地 history（不存版本）

**决策**：
- 主题编辑面板在内存里维护 history stack（每个改动 = 一个 entry）
- "撤销"按钮 = pop history，"重做" = push 回
- "保存"后才创建 theme_version（持久化）
- 关闭编辑器/刷新 = 丢失未保存改动（toast 提示"未保存"）

**为什么**：本地撤销比"来回切 server 版本"快 100 倍，UX 顺滑。

### C4. 发布中 UX = 后台任务 + 进度条 + 通知

**决策**：
- `POST /publish` 返回 202 Accepted + `job_id`
- 前端跳到 `/sites/{id}/publish` 发布页，显示任务列表 + 进度
- 进度更新：前端轮询 `GET /publish/jobs/{id}`（2s 一次），不阻塞用户
- 完成 / 失败：toast 通知 + 列表项标色（绿/红）
- 失败时可点"重试" = 重新创建 job（基于同一 theme_version）

**为什么**：构建 30s-3min，不能让用户卡在按钮上。

### C5. 发布历史回滚 = 切换 nginx serve 路径

**决策**：
- `POST /publish/history/{id}/rollback` = 创建新 deployment（status=success 立即完成），artifact_path = 旧 deployment 的 artifact_path 软链
- 不删除旧 deployment 数据（保留历史）
- 回滚后用户可"再回滚到回滚前"（任意切换）

**为什么**：保留所有历史可回溯。磁盘成本可接受（每站最多保留 10 个 deployment，超出 LRU 清理）。

### C6. 内容改完触发重发布 = 手动 + 提示

**决策**：
- 内容状态变 published 后**不自动触发发布**
- toast 提示"已发布，是否立即更新公开站？" + 按钮"立即发布"
- 批量改完一批内容后，一次性发布

**为什么**：自动发布会让用户改 1 字就触发 30s 构建，体验差。

### C7. 公开站 = 仅 published 内容 + Last built 标识

**决策**：
- SSG 构建时只拉 `content_snapshots`（已经发布过的快照）
- 公开站 footer 显示 `Last built: 2026-06-05 13:45`
- 公开站任何修改都依赖"再发布"动作

**为什么**：SSG 静态站不能动态拉新发布的内容（除非 SSR），但静态是性能优势。

### C8. 主题编辑器 = 2-3 个"预设"快捷按钮 + 完整 token 面板

**决策**：
- 主题编辑器顶部加 3 个快捷按钮：
  - "更暗"（自动调 primary/text/bg 偏暗一档）
  - "更亮"（偏亮）
  - "更大字"（fontSize 全部 ×1.2）
- 下面是完整 token 面板（color/typography/spacing/radius 4 个 tab）

**为什么**：P2 用户大多是"想换换风格"而不是"从头设计"，预设按钮降低门槛。P3 加 AI 调样式就是终极版（"调成暗黑风" → AI 改全套）。

## D. 技术实现细节

### D1. SSG 容器 = worker 容器内置 Node 25.8.1

**决策**：
- 不独立 SSG 容器
- worker 容器 = Python (Celery) + Node 25.8.1 (Astro CLI)
- worker 跑构建 = `subprocess.run(['npx', 'astro', 'build', ...])`
- 容器镜像 = `python:3.11-slim` + `apt install nodejs npm` + `npm install -g pnpm` + 项目 `pnpm install`

**为什么**：少一个容器 = 少一份配置 + 少一个网络调用。代价 = 镜像大一些（+200MB），可接受。

### D2. Astro 项目位置 = `ssg/_template/`

**决策**：
- `ssg/_template/` 唯一模板（5 主题共享，token 不同）
- 构建时 = 复制 _template 到 `/tmp/build/{site_id}/` → 注入当前主题 tokens → 注入内容数据 → `astro build` → 产物 copy 到 `/data/sites/{site_id}/public/`
- **不** `ssg/sites/_template/`（04a 写错）也**不** `ssg/themes/<name>/`（5 套模板违反 07 §"一套模板 + token 控制"原则）

### D3. Block 渲染器技术栈 = .astro + unified/remark

**决策**（详见 04a §4.3 修订）：
- Block 组件 = `.astro`（不是 .tsx，不引入 React）
- Tiptap JSON → HTML = `unified/remark/rehype` 管线
- 客户端预览组件 = 复用同一份 `tiptap-to-html` 包（共享代码）

### D4. Tiptap JSON 渲染 = unified/remark + 自定义 handler

**决策**：
- Tiptap 默认 7 种节点类型：doc/paragraph/heading/text/bold/italic/...
- 加自定义节点：callout/codeBlock/image
- 渲染管线 = `unified().use(remarkTiptap).use(remarkRehype).use(rehypeStringify)`
- 自定义节点写 remark plugin（add handler）

**为什么**：unified 是 Node 生态最成熟的 markdown/HTML 处理库，性能好（流式）。

### D5. 发布触发 = 手动（API）+ Celery 异步

**决策**：
- 手动 = `POST /publish` 立即入 Celery 队列，返回 202
- 自动 = `scheduled_publishes` 表（P3）由 Celery Beat 每分钟扫
- 同步触发 = **不提供**（前端 UI 体验差）

### D6. 移除 `cdn_purged` 字段

**决策**：P2 不接 CDN，nginx 直 serve。`cdn_purged` 字段从 deployments 表移除。

**为什么**：当前阶段没 CDN，加字段是 YAGNI。

### D7. 主题复制 = `POST /themes` with `base_theme_id`

**决策**：
- 用户在 default 主题编辑器里改完点"另存为新主题" → 弹窗输入名字 → 创建新 themes 行
- `type='custom'`, `base_theme_id=default.id`, `default_tokens=当前编辑的 tokens`
- 创建后该主题出现在主题库，用户可应用到其他站

**API 端点**：
- `POST /themes` body = `{code, display_name, base_theme_id, default_tokens}` → 创建 custom 主题
- `GET /themes?type=custom&author_id=me` 列出我创建的 custom 主题

## E. 可观测性 / 监控

### E1. 构建日志 = `build_log` 字段保存尾部 64KB

**决策**：
- worker 跑 `astro build` 时，subprocess stdout 收集到 buffer
- 超过 64KB 截断（保留最后部分）
- 任务完成 / 失败时写入 `deployments.build_log`
- 失败时 100% 保留（不截断）

**API 端点**：`GET /publish/jobs/{id}` 返回 `build_log` 字段

### E2. 部署超时 = 10 分钟（可配）

**决策**：
- Celery task `soft_time_limit=540` (9 分钟) + `time_limit=600` (10 分钟)
- 超时 = deployment.status='failed', error_message='构建超时 (>10min)'
- 配置项：将来可加 `site.build_timeout` 字段（本期先硬编码）

### E3. 多 worker 串行构建 = 1 worker 1 任务

**决策**：
- worker prefetch=1（已配），保证 1 worker 同时只跑 1 任务
- worker 数 = CPU 核数（默认 2，可配）
- 队列名 = `publish`（与其他任务隔离）

### E4. 失败重试 = 自动 1 次 + 手动任意次

**决策**：
- 首次失败 = 自动重试 1 次（`retry_count` 字段递增）
- 二次失败 = 不再重试，标记 failed
- 手动 = 失败任务列表有"重试"按钮 → 创建新 deployment（不修改原任务）

## F. 安全 / 合规

### F1. content_snapshots 软删策略

**决策**：
- content 软删（deleted_at）**不影响** snapshot（snapshot 本身是发布历史）
- content hard delete（罕见，30 天后自动清理）→ snapshot ON DELETE CASCADE 删
- GDPR 删除请求 = hard delete content → snapshot 跟着删 ✓

### F2. 主题 token 注入 = 写入前 sanitize

**决策**：
- token value 是 CSS 字符串（如 `#3b82f6` / `0 4px 6px rgba(0,0,0,.1)` / `Inter, sans-serif`）
- 写入 DB 前正则校验：`color.*` 必须 `#[0-9a-fA-F]{3,8}` 或 `rgb()/rgba()/hsl()`；`fontFamily.*` 限制字符集
- 不允许 `<` `>` `"` `'` 出现在 token value 中

**实现要点**：用 Pydantic validator + regex。

### F3. 站点归档 = 公开站 410 Gone

**决策**：
- 站点 status='archived' → 公开站返回 410 Gone（不是 404，避免 SEO 误判）
- nginx 配置：`if ($site_archived) { return 410; }`
- 状态切回 active → 公开站立即恢复
