## 1. 架构概览

### 1.1 8 个容器一览

| # | 服务 | 镜像 / 构建 | 职责 | 端口 (host) |
|---|------|------------|------|------------|
| 1 | `postgres` | `postgres:16-alpine` | 主库（21 张表） | 5432 |
| 2 | `redis` | `redis:7-alpine` | 缓存 + Celery 队列 | 6379 |
| 3 | `minio` | `minio/minio:latest` | S3 兼容对象存储（媒体 + 备份） | 9000 / 9001 |
| 4 | `api` | `backend/Dockerfile` | FastAPI + uvicorn（业务） | 8000 |
| 5 | `worker` | `backend/Dockerfile` | Celery Worker（发布 / 缩略图 / AI） | — |
| 6 | `beat` | `backend/Dockerfile` | Celery Beat（定时任务：状态机轮询） | — |
| 7 | `admin` | `frontend/Dockerfile.dev` | Vite dev server（开发模式） | 5173 |
| 8 | `nginx` | `deploy/nginx/Dockerfile` | 反代 + 静态托管 + 域名路由 | 80 |

> **生产环境**通常把 `admin` 改成构建产物 + nginx 直接服务，去掉 Vite dev server（见 §3.6 优化）。

### 1.2 网络拓扑

```
                Internet
                   │
            ┌──────▼──────┐
            │    nginx    │ :80
            │  (反代 + 静态)
            └──┬─────┬────┘
               │     │
        /api/v1│     │/admin, /
               │     │
        ┌──────▼─┐ ┌─▼──────┐
        │   api  │ │ admin  │
        │ :8000  │ │ :5173  │   ←── 仅开发用
        └──┬─────┘ └────────┘
           │
   ┌───────┼───────┐
   │       │       │
┌──▼──┐ ┌──▼──┐ ┌──▼──┐
│ pg  │ │redis│ │minio│
│ :5432│ │:6379│ │:9000│
└─────┘ └─────┘ └─────┘
   ▲                   ▲
   │      ┌────────┐    │
   │      │ worker │────┘
   │      │  +beat │
   │      └────────┘
```

**网络**：`ai_cms_net`（bridge）— 容器间通过服务名访问（`api` / `postgres` / `redis` / `minio`）。

### 1.3 数据流向

| 路径 | 流向 | 落盘位置 |
|------|------|---------|
| 用户内容 | admin → api → postgres | `pg_data` volume |
| 媒体上传 | admin → api (presign) → minio (直传) | `minio_data` volume |
| 静态发布 | worker (Celery) → Astro 构建 → 文件 | `sites_data` volume（可选 host bind mount） |
| 域名映射 | api 写 `sites.map` → nginx inotify reload | `nginx_conf` volume |
| 备份 | backup 容器 → pg_dump → gzip → minio | `backups` bucket |

## 2. 前置要求

### 2.1 硬件

| 场景 | CPU | 内存 | 磁盘 | 说明 |
|------|-----|------|------|------|
| 演示 / 内测 (≤ 5 站) | 2 核 | 4 GB | 20 GB | 本机 / 单核云 |
| 小生产 (≤ 50 站) | 4 核 | 8 GB | 100 GB | 2 核云 |
| 中生产 (50-500 站) | 8 核 | 16 GB | 500 GB SSD | 4 核云 + 独立 DB |
| 大生产 (500+ 站) | 16 核+ | 32 GB+ | 1 TB+ SSD + 备份盘 | 多实例 + 负载均衡 |

> **关键点**：`minio_data` 和 `pg_data` 是命脉。**用 SSD**（发布产物的 SSG 构建 IO 密集）。

### 2.2 软件

| 软件 | 版本 | 用途 |
|------|------|------|
| Docker | 24.0+ | 容器运行时 |
| Docker Compose | v2.20+ | 多容器编排 |
| 域名 | 1 个 + DNS | 站点访问 |
| (可选) Caddy | 2.7+ | 自动 HTTPS |

### 2.3 端口预留

**避免与以下服务冲突**：

| 端口 | 占用 | 建议改 |
|------|------|--------|
| 80 | nginx | 改 `NGINX_PORT=8080` |
| 5432 | postgres | 改 `POSTGRES_PORT=25432` |
| 6379 | redis | 改 `REDIS_PORT=26379` |
| 9000/9001 | minio | 改 `MINIO_PORT=9090` |
| 8000 | api | 改 `API_PORT=18888` |
| 5173 | admin dev | 改 `FRONTEND_PORT=18889` |

> **生产建议**：5432 / 6379 / 9000/9001 全部改为非默认端口（避免被扫描），nginx 80 → 443 + 内网 8000。

### 2.4 域名 / DNS

最少 1 个域名。建议规划：

- `admin.example.com` → 后台入口
- `www.example.com` → 站点 1
- `blog.example.com` → 站点 2
- `*.example.com` → 多租户（可选）

DNS 解析：`admin.example.com` 和所有站点域名都 A 记录到**服务器公网 IP**（nginx 会按 `Host` 头分发）。

## 3. 生产部署（从 0 到 1）

### 3.1 拉取代码

```bash
git clone https://github.com/<your-org>/ai-cms.git /opt/ai-cms
cd /opt/ai-cms

# 切到稳定 tag（生产不要用 main）
git checkout v0.4.0
```

### 3.2 配置 .env

```bash
cp deploy/.env.example deploy/.env
vim deploy/.env
```

**必改项**（生产强制）：

```bash
# ====== 全局 ======
PROJECT_NAME=ai-cms-prod     # 多个 ai-cms 实例共存时区分
TZ=Asia/Shanghai

# ====== Postgres（强密码，22+ 字符） ======
POSTGRES_USER=ai_cms
POSTGRES_PASSWORD=$(openssl rand -base64 32)  # ← 改
POSTGRES_DB=ai_cms
POSTGRES_PORT=25432          # ← 改非默认

# ====== MinIO（同上） ======
MINIO_ROOT_USER=ai_cms
MINIO_ROOT_PASSWORD=$(openssl rand -base64 32)  # ← 改
MINIO_PORT=9090              # ← 改非默认
MINIO_CONSOLE_PORT=9091
# 公开访问 URL（站点里 <img src=...> 用这个）
MINIO_PUBLIC_URL=https://media.example.com    # ← 改你的域名

# ====== Backend ======
API_PORT=18888               # ← 改非默认
# 关键：32+ 字节随机串，丢失 = 全部 token 失效
SECRET_KEY=$(openssl rand -base64 48)         # ← 必改！
ACCESS_TOKEN_EXPIRE_MINUTES=15
REFRESH_TOKEN_EXPIRE_DAYS=7
# CORS：列出所有允许的 origin，逗号分隔（**禁用 * **）
CORS_ORIGINS=https://admin.example.com,https://example.com
# ENV=prod 触发 HSTS（安全头中间件 §P4.2）
ENV=prod

# ====== Frontend ======
FRONTEND_PORT=18889
# 前端构建时用，最终 API 地址（容器内可写服务名 api）
VITE_API_BASE=/api/v1

# ====== Nginx ======
NGINX_PORT=80

# ====== 备份 ======
MINIO_BACKUP_BUCKET=backups
BACKUP_RETENTION_DAYS=30     # 生产建议 30 天

# ====== 站点产物（推荐 host 可访问） ======
SITES_DATA_HOST_PATH=/var/lib/ai-cms/sites   # ← bind mount 到 host

# ====== AI Providers ======
AI_DEFAULT_PROVIDER=minimax  # 见 §4
MINIMAX_API_KEY=...
```

> 🔒 **SECRET_KEY 一定保存**到密码管理器。丢了 = 全部 access token 失效（用户需重登）。
> 🔒 **POSTGRES_PASSWORD / MINIO_ROOT_PASSWORD** 必改，否则**默认密码 `change_me_pg` / `change_me_minio` 是公开漏洞**。

### 3.3 启动服务

```bash
cd /opt/ai-cms/deploy

# 启动
docker compose up -d

# 看状态（等 30s 让 healthcheck 过）
docker compose ps
```

**预期输出**（8 容器全 healthy）：

```
SERVICE    STATE    STATUS
admin      running  Up X minutes
api        running  Up X minutes
beat       running  Up X minutes
minio      running  Up X minutes (healthy)
nginx      running  Up X minutes
postgres   running  Up X minutes (healthy)
redis      running  Up X minutes (healthy)
worker     running  Up X minutes
```

### 3.4 初始化数据库

```bash
# 1. 跑迁移
docker compose exec api alembic upgrade head

# 2. 验证迁移版本
docker compose exec api alembic current
# 应输出: 0037 (head)  ← 数字跟当前代码版本走
```

### 3.5 种子演示数据（**生产可选**）

```bash
# 演示数据：1 站 + 5 用户 + 3 栏目 + 10 文章
docker compose exec api python scripts/seed_demo.py --reset

# 统一密码 demo123456（**生产用完即改 / 删 demo 用户**）
```

**生产建议**：
- 内测阶段：种子数据有用
- 正式运营：**不跑 seed_demo.py**，直接在 admin UI 注册第一个 super admin

### 3.6 (可选) 启用 backup 容器

见 §7.1。备份服务**默认不启动**（`docker-compose.yml` 注释里写明了），需要手动启用。

### 3.7 (可选) 前端生产构建

开发模式用 Vite dev server（`admin` 容器）。**生产建议改成 build 产物**：

```bash
cd frontend
pnpm install --frozen-lockfile
pnpm build        # 产物在 dist/
```

然后在 `docker-compose.yml` 里把 `admin` service 替换为：

```yaml
  # 生产 frontend
  admin-prod:
    image: nginx:alpine
    volumes:
      - ./frontend/dist:/usr/share/nginx/html:ro
      - ./deploy/nginx/admin.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      - api
    networks:
      - ai_cms_net
```

`admin.conf` 配 SPA fallback：

```nginx
server {
    listen 80;
    server_name _;
    root /usr/share/nginx/html;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

> **生产 frontend 优势**：省一个 dev server 进程 + HMR 攻击面消失 + 启动 1s vs 30s。

### 3.8 验证

```bash
# 1. 健康检查（**根路径**）
curl -I http://localhost/healthz
# 期望: HTTP/1.1 200 OK

# 2. 登录拿 token
curl -X POST http://localhost/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@aicms.io","password":"demo123456"}'
# 期望: {"code":0,"message":"ok","data":{"access_token":"...","refresh_token":"...","user":{...}}}

# 3. 访问 /admin
curl -I http://localhost/admin/
# 期望: 200 + index.html
```

## 4. AI Provider 配置

AI-CMS 抽象层（litellm）支持 5 个 provider。**生产推荐 `minimax`（中文强 + 国内快）** 或 `openai`。

### 4.1 Provider 矩阵

| Provider | 配置项 | 适用场景 | 备注 |
|----------|--------|---------|------|
| `openai` | `OPENAI_API_KEY` | 海外 / GPT-4o | 需科学上网 |
| `anthropic` | `ANTHROPIC_API_KEY` | Claude | 需科学上网 |
| `minimax` | `MINIMAX_API_KEY` | 国内 / 中文 | **默认推荐** |
| `ollama` | `OLLAMA_BASE_URL` | 本地 / 隐私 | 需 GPU + 8B+ 模型 |
| `custom` | (env 自定义) | 自建网关 | 走 OpenAI 兼容协议 |

### 4.2 选 provider

```bash
# .env
AI_DEFAULT_PROVIDER=minimax
MINIMAX_API_KEY=eyJhbGc...
MINIMAX_BASE_URL=https://api.minimaxi.com/v1
MINIMAX_DEFAULT_MODEL=abab6.5s-chat
```

### 4.3 多个 provider 混用

admin UI `/admin/ai-providers` 可加多个 provider 实例。**`AI_DEFAULT_PROVIDER` 是兜底**，用户在 AI 助手下拉框切换。

### 4.4 限流

Celery worker 默认无并发限制。生产建议加：

```bash
# .env
CELERY_WORKER_CONCURRENCY=4   # 默认等于 CPU 核数
```

> AI 调用通常长任务（10-60s），worker 并发过高会卡。**保守设 2-4**。

### 4.5 监控成本

```bash
# 看每个 provider 的 token 用量
docker compose exec api python -c "
import asyncio
from app.db.session import AsyncSessionLocal
from app.models.ai import AIUsage
from sqlalchemy import select, func
async def main():
    async with AsyncSessionLocal() as db:
        r = await db.execute(
            select(AIUsage.provider, func.sum(AIUsage.total_tokens))
            .group_by(AIUsage.provider)
        )
        for provider, tokens in r.all():
            print(f'{provider}: {tokens:,} tokens')
asyncio.run(main())
"
```

## 5. HTTPS / 反向代理

### 5.1 推荐：Caddy（自动续签）

[Caddy](https://caddyserver.com) 自动 Let's Encrypt 证书 + HTTP/2 + 自动续签。

**主机装 Caddy**（不用 docker，更可靠）：

```bash
# macOS
brew install caddy

# Debian/Ubuntu
sudo apt install -y debian-keyring debian-archive-keyring apt-transport-https
curl -1sLf "https://dl.cloudsmith.io/public/caddy/stable/gpg.key" | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
echo "deb [signed-by=/usr/share/keyrings/caddy-stable-archive-keyring.gpg] https://dl.cloudsmith.io/public/caddy/stable/deb/debian any-version main" | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo apt update && sudo apt install caddy
```

`/etc/caddy/Caddyfile`：

```caddyfile
# 管理后台
admin.example.com {
    reverse_proxy 127.0.0.1:80 {
        # 透传 Host 头 (nginx 内部需要)
        header_up Host {host}
    }
    encode gzip zstd
}

# 站点 1
example.com, www.example.com {
    reverse_proxy 127.0.0.1:80 {
        header_up Host {host}
    }
    encode gzip zstd
}

# 站点 2
blog.example.com {
    reverse_proxy 127.0.0.1:80 {
        header_up Host {host}
    }
    encode gzip zstd
}

# MinIO 公开访问（媒体直链）
media.example.com {
    reverse_proxy 127.0.0.1:9090
}
```

```bash
sudo systemctl reload caddy
# Caddy 自动申请证书、配置 HSTS、HTTP/2
```

### 5.2 替代：nginx + certbot

如果不引入 Caddy，直接让 80 端口走 certbot：

```bash
sudo apt install certbot python3-certbot-nginx
sudo certbot --nginx -d admin.example.com -d example.com
```

按提示会自动改 `/etc/nginx/sites-enabled/default`，加 443 块和证书路径。

### 5.3 让 docker nginx 监听 127.0.0.1

`deploy/.env`：

```bash
NGINX_PORT=127.0.0.1:80   # 只接受本机反代
```

> 这样外网只能通过 Caddy/certbot 访问，**docker nginx 不直接暴露公网**（更安全）。

### 5.4 HSTS（强制 HTTPS）

`backend/app/main.py` 的 `security_headers` 中间件**只在 `ENV=prod` 时加 HSTS**（P4.2 实现）：

```
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

确认 `.env` 设了 `ENV=prod`。

## 6. 多域名 / host-based 站点映射

### 6.1 工作机制

AI-CMS 支持**一个 admin 管多个独立站点**，每个站点绑一个或多个域名。

```
http_host            →  host_to_slug  →  静态文件路径
example.com          →  "my-site"     →  /var/www/sites/my-site/
www.example.com      →  "my-site"     →  /var/www/sites/my-site/
blog.example.com     →  "blog"        →  /var/www/sites/blog/
admin.example.com    →  ""            →  /admin/  (回退)
```

### 6.2 sites.map 文件

由后端自动维护：`/etc/nginx/conf.d/sites.map`

```
example.com my-site;
www.example.com my-site;
blog.example.com blog;
```

**格式**：`<空格分隔域名> <空格分隔 slug>;` 每行一对，nginx map 语法。

### 6.3 nginx 自动 reload

`deploy/nginx/entrypoint.sh` 启动 `inotifywait` 监听 `sites.map`，文件改动 200ms 后自动 `nginx -s reload`。**无需手动 reload**。

### 6.4 绑定域名（admin UI）

1. 登录 `/admin/sites`
2. 选站点 → 「域名」tab
3. 添加 `example.com` + `www.example.com`（都映射到这个站）
4. 保存 → 后端写 `sites.map` → nginx 自动 reload
5. DNS A 记录 `example.com → <server_ip>` 即可访问

### 6.5 调试映射

```bash
# 查 map 文件
docker compose exec api cat /etc/nginx/conf.d/sites.map

# 测域名解析
docker compose exec nginx nginx -T | grep -A 5 "host_to_slug"

# 直接 curl 测
curl -H "Host: example.com" http://localhost/  # 应返回站点首页
```

## 7. 备份与恢复

### 7.1 启用 backup 容器

`deploy/docker-compose.yml` 末尾**取消注释**（搜索 `# backup 块删除`）：

```yaml
  backup:
    build:
      context: ./backup
      dockerfile: Dockerfile
    container_name: ${PROJECT_NAME:-ai-cms}-backup
    restart: unless-stopped
    env_file: .env
    environment:
      POSTGRES_HOST: postgres
      POSTGRES_PORT: 5432
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
      MINIO_ENDPOINT: minio:9000
      MINIO_ROOT_USER: ${MINIO_ROOT_USER}
      MINIO_ROOT_PASSWORD: ${MINIO_ROOT_PASSWORD}
      MINIO_BACKUP_BUCKET: ${MINIO_BACKUP_BUCKET:-backups}
      MINIO_USE_SSL: "false"
      BACKUP_RETENTION_DAYS: ${BACKUP_RETENTION_DAYS:-7}
      TZ: ${TZ}
    depends_on:
      postgres:
        condition: service_healthy
      minio:
        condition: service_healthy
    volumes:
      - ./backup/backup.sh:/usr/local/bin/backup.sh:ro
    networks:
      - ai_cms_net
```

```bash
docker compose up -d backup
docker compose ps backup  # 应 running
```

### 7.2 手动备份

```bash
# 立即跑一次（不依赖 cron）
docker compose exec backup /usr/local/bin/backup.sh

# 测连通性
docker compose exec backup /usr/local/bin/backup.sh --test
# 期望: ✅ 连通性测试通过
```

**产物路径**：`minio://backups/YYYYMMDD/pg_ai_cms_YYYYMMDDTHHMMSSZ.sql.gz`

### 7.3 定时

`deploy/backup/crontab` 默认 `0 3 * * *`（每天 3:00 Asia/Shanghai）。改频率直接编辑该文件 + `docker compose restart backup`。

### 7.4 验证备份完整性

```bash
# 列出最近 7 天备份
docker compose exec backup mc ls --recursive backup/backups/ | tail -10

# 下载 + 解压 + 看头几行
LATEST=$(docker compose exec backup mc ls backup/backups/ | tail -1 | awk '{print $NF}')
docker compose exec backup mc cat "backup/backups/$LATEST" > /tmp/test.sql.gz
gunzip -c /tmp/test.sql.gz | head -20
# 期望: 看到 CREATE TABLE / INSERT 等 SQL
```

### 7.5 恢复

**场景**：postgres 数据全丢，从最新备份恢复。

```bash
# 1. 找最新备份
LATEST=$(docker compose exec backup mc ls --recursive backup/backups/ | sort | tail -1 | awk '{print $NF}')
echo "Latest: $LATEST"

# 2. 下载到本地
docker compose exec backup mc cat "backup/backups/$LATEST" > /tmp/restore.sql.gz

# 3. 灌回 postgres（**这会覆盖当前数据！**）
gunzip -c /tmp/restore.sql.gz | docker compose exec -T postgres psql \
  -U "$POSTGRES_USER" \
  -d "$POSTGRES_DB"

# 4. 验证
docker compose exec postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT count(*) FROM sites;"
# 期望: 站点数（应该跟备份时一致）
```

### 7.6 媒体 / 站点产物备份

当前 `backup.sh` **只备份 PG**。媒体（minio）和站点产物（sites_data）需另备份：

```bash
# 方案 A：用 mc mirror 镜像到第二个 MinIO
docker run --rm --network deploy_ai_cms_net \
  -e MC_HOST_minio="http://$MINIO_ROOT_USER:$MINIO_ROOT_PASSWORD@minio:9000" \
  minio/mc mirror --remove --overwrite \
  minio/media /backup/media/$(date +%Y%m%d)

# 方案 B：直接 rsync volume（停机时）
docker compose stop
sudo rsync -a /var/lib/docker/volumes/deploy_minio_data/ /backup/minio/
sudo rsync -a /var/lib/ai-cms/sites/ /backup/sites/
docker compose start
```

> 生产建议：**A 方案**，热备不停机。

## 9. 性能调优

### 9.1 Postgres

`deploy/docker-compose.yml` 的 `postgres.command` 改为自定义调参：

```yaml
  postgres:
    command: >
      postgres
      -c shared_buffers=256MB
      -c max_connections=200
      -c effective_cache_size=1GB
      -c work_mem=4MB
      -c maintenance_work_mem=128MB
      -c random_page_cost=1.1
      -c log_min_duration_statement=500
```

**经验值**（4 核 8GB 机器）：
- `shared_buffers` = 内存的 25%
- `effective_cache_size` = 内存的 75%
- `work_mem` = 内存的 5% / max_connections

### 9.2 Redis

默认配置够用。慢查询场景加：

```yaml
  redis:
    command: >
      redis-server
      --appendonly yes
      --maxmemory 512mb
      --maxmemory-policy allkeys-lru
      --slowlog-log-slower-than 10000
```

### 9.3 API（uvicorn worker 数）

`backend/Dockerfile` 默认 `uvicorn ... --workers 1`（dev `--reload`）。生产改：

```dockerfile
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "4"]
```

**经验值**：worker 数 = 2 × CPU 核数。每个 worker ~200MB 内存。

### 9.4 Celery worker

```bash
# .env
CELERY_WORKER_CONCURRENCY=4   # 跟 CPU 核数走
```

发布任务（SSG 构建）**是 IO 密集**，可适当调高到 6-8。AI 任务**是网络密集**，保持 2-4。

### 9.5 静态发布

`/var/www/sites/` 容器内目录建议**直接挂 host 高速 SSD**（不是 named volume）：

```bash
# .env
SITES_DATA_HOST_PATH=/var/lib/ai-cms/sites
```

生产 100+ 站发布，**首次 build 慢**（10-30s/站）。优化：
- Astro 增量构建已开（`clean_before=False`）
- 启用 `ASTRO_ENABLED=true`（用 Astro 4 替代纯 Python 渲染器）
- 并发 worker：8-12 核机器设 6 worker

### 9.6 nginx

`deploy/nginx/nginx.conf` 已开 `gzip`。**生产加 brotli**：

```nginx
# 替换 gzip 段
brotli on;
brotli_comp_level 6;
brotli_types text/plain text/css application/json application/javascript text/xml application/xml image/svg+ml;
brotli_static on;
```

需要 `nginx-extras` 镜像或自编译。

## 11. 常见问题 / 故障排查

### 11.1 容器一直 Restarting

**症状**：`docker compose ps` 显示某服务 `Restarting`。

**排查**：

```bash
docker compose logs --tail=30 <service>
# 看最后报错，常见：
# - ModuleNotFoundError: pyproject.toml 加了新依赖，镜像没重建 → docker compose build <service>
# - ConnectionError: 等依赖服务起来 → 看 depends_on healthcheck
# - Permission denied: volume 权限问题 → chmod 777 data dir
```

### 11.2 nginx 502 Bad Gateway

**症状**：访问站点返回 502。

**排查**：

```bash
# 1. api 容器活着吗
docker compose ps api

# 2. nginx 能解析到 api 吗
docker compose exec nginx nslookup api
# 期望: 172.x.x.x

# 3. api 端口监听了吗
docker compose exec api curl http://localhost:8000/api/v1/healthz

# 4. nginx → api 网络通吗
docker compose exec nginx curl -m 3 http://api:8000/api/v1/healthz
```

**常见原因**：
- DNS 缓存：`deploy/nginx/nginx.conf` 已用 `resolver 127.0.0.11 valid=10s` 解决
- api 还没启动完：等 10s 重试
- api 挂了：看 `docker compose logs api`

### 11.3 静态发布卡住

**症状**：发布按钮一直转圈，部署记录 status=pending。

**排查**：

```bash
# 1. worker 活着吗
docker compose ps worker

# 2. celery 队列堆积
docker compose exec redis redis-cli LLEN celery
# 期望 < 10

# 3. 看具体任务
docker compose logs --tail=20 worker | grep -A 5 "publish"

# 4. 强制重启 worker（清缓存）
docker compose restart worker
```

**已知原因**（P3.6.1 修复）：改 backend 代码后**必须重启 worker**（uvicorn --reload 不带 worker）。

### 11.4 MinIO 上传 403

**症状**：admin 上传媒体失败。

**排查**：

```bash
# 1. bucket 存在吗
docker compose exec minio mc ls local/
# 期望看到 media

# 2. 手动建 bucket
docker compose exec minio mc mb local/media
docker compose exec minio mc anonymous set download local/media

# 3. 查 CORS
docker compose exec minio mc admin info local
```

### 11.5 AI 调用超时

**症状**：AI 助手一直转圈，30s 后报错。

**排查**：

```bash
# 1. 测 provider 连通
docker compose exec api python -c "
import httpx
r = httpx.get('$MINIMAX_BASE_URL/models', headers={'Authorization': 'Bearer $MINIMAX_API_KEY'}, timeout=10)
print(r.status_code, r.text[:200])
"

# 2. 改超时
# .env
AI_TIMEOUT_SECONDS=120

# 3. 换 provider
AI_DEFAULT_PROVIDER=openai
```

### 11.6 前端 HMR 失效 / 路由 404

**症状**：admin 页面改代码后浏览器没自动刷新，或刷新后 404。

**排查**：

```bash
# 1. 清 Vite 缓存
docker compose exec admin rm -rf node_modules/.vite
docker compose restart admin

# 2. 重新装依赖（lock 改了之后）
docker compose exec admin pnpm install --no-frozen-lockfile
```

### 11.7 域名访问错站

**症状**：访问 `blog.example.com` 看到 `example.com` 的站。

**排查**：

```bash
# 1. 看 sites.map
docker compose exec api cat /etc/nginx/conf.d/sites.map

# 2. 看 host_to_slug 解析
docker compose exec nginx nginx -T 2>&1 | grep -A 20 "host_to_slug"

# 3. 加域名映射（admin UI /sites → 域名 tab）
```

### 11.8 磁盘满

**症状**：发布失败，DB 写入失败。

```bash
# 看哪占的多
docker system df
du -sh /var/lib/docker/volumes/*

# 清理
docker system prune -a         # 清无用镜像
docker volume prune            # 清无用 volume（⚠️ 别误删 pg_data）
```

**定期任务**：
```bash
# /etc/cron.daily/ai-cms-cleanup
docker system prune -af --filter "until=72h"   # 72h 前镜像
find /var/lib/ai-cms/sites/*/.cache -mtime +7 -delete  # SSG 缓存
```

### 11.9 升级后 alembic 报 "relation does not exist"

**症状**：升级后 API 启动报某张表不存在。

**原因**：迁移没跑全。

**修复**：

```bash
docker compose exec api alembic upgrade head
# 看是不是有 "table X already exists" → 手动改 alembic_version
docker compose exec postgres psql -U ai_cms -d ai_cms -c \
  "UPDATE alembic_version SET version_num='<last_good_version>';"
docker compose exec api alembic upgrade head
```

### 11.10 backup 容器卡死

```bash
# 看 supercronic 状态
docker compose exec backup ps aux | grep supercronic

# 看最近备份日志
docker compose logs --tail=30 backup

# 手动跑一次
docker compose exec backup /usr/local/bin/backup.sh
```

### 11.11 worker/beat 报 `ModuleNotFoundError: No module named 'PIL'`

**症状**：P4.2 后启动 beat 报 PIL 找不到，重复重启。

**原因**：beat/worker 镜像是早期构建，PIL 后加进 pyproject.toml 没 rebuild。

**修复**：

```bash
cd deploy
docker compose build beat worker
docker compose up -d beat worker
docker compose ps   # 验证 running
```

> 未来加新 pyproject 依赖 → **必须 rebuild api/worker/beat**（共享 Dockerfile）。

### 11.12 TOKEN 一直 401

**症状**：登录后所有请求 401。

**原因 1**：`.env` 改了 `SECRET_KEY`，旧 token 失效 → 重登。

**原因 2**：dev_token 缓存过期（15min 有效，P4.1 发现并修过）→ 重跑 `bash backend/scripts/dev_token.sh`。

**原因 3**：CORS 不允许当前 origin → 看浏览器 Network 是不是 OPTIONS 405。

## 12. 回滚 / 灾难恢复

### 12.1 场景矩阵

| 场景 | 影响 | 恢复时间 | 步骤 |
|------|------|---------|------|
| 单容器崩 | 局部 | < 1 min | `docker compose restart <service>` |
| 代码 bug | API 异常 | < 5 min | git checkout 旧 tag + rebuild |
| DB 数据误删 | 数据丢失 | 5-30 min | 恢复 PG 备份（§7.5） |
| 主机磁盘坏 | 全失 | 数小时 | 用 MinIO 备份 + 重建主机 |
| 误删 minio media | 媒体丢失 | 5-30 min | 用 mc mirror 恢复（§7.6） |

### 12.2 完整灾难恢复（主机全失）

```bash
# 1. 新主机：装 docker
curl -fsSL https://get.docker.com | sh

# 2. 拉代码
git clone https://github.com/<org>/ai-cms.git /opt/ai-cms
cd /opt/ai-cms
git checkout v0.4.0   # 跟旧主机一致

# 3. 恢复 .env（从密码管理器 / 备份）
# 关键: SECRET_KEY, POSTGRES_PASSWORD, MINIO_ROOT_PASSWORD 必须跟旧主机一致
# 否则旧的 token + MinIO bucket 都没法解密

# 4. 启动
cd deploy
docker compose up -d
docker compose exec api alembic upgrade head

# 5. 恢复 PG
# (从 MinIO 备份下载, 见 §7.5)

# 6. 恢复 MinIO 媒体（如果有异地 mirror）
docker run --rm --network deploy_ai_cms_net \
  minio/mc mirror /backup/media minio/media

# 7. 验证
curl http://localhost/api/v1/healthz
```

> **关键**：`SECRET_KEY` 跟 `POSTGRES_PASSWORD` / `MINIO_ROOT_PASSWORD` 是命脉。**用密码管理器 1Password / Bitwarden 存**。

### 12.3 异地容灾

**生产建议**：
- 备份 MinIO bucket `backups` 跨区域镜像（mc mirror 加 cron）
- 关键 secret 同步到密码管理器
- DNS 切到新 IP 的 RTO < 30 min
